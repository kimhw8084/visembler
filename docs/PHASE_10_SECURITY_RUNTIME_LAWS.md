# Phase 10 — Security & Runtime Laws

These rules are framework contracts for humans and Gemma/OpenCode.

## Authentication & authorization

1. Authentication establishes identity; authorization separately determines access.
2. UI visibility is never authorization. Protected data/actions must be checked server-side.
3. Identity headers are accepted only through a trusted boundary. Use trusted network verification and/or the proxy assertion secret.
4. Never trust browser-supplied role/permission values directly.
5. Protected NiceGUI pages must execute `runtime.require_http(request, policy)` before rendering protected content or querying protected data.
6. Do not use `app.storage.user` as the authentication source of truth.
7. Company OIDC/SAML specifics belong in a dedicated `AuthenticationAdapter`; application pages consume `Principal` only.

## NiceGUI session/security

8. User/browser storage requires `storage_secret`; production configuration fails closed if it is absent.
9. Production session cookies default to `https_only=True` and `same_site='strict'`.
10. Secrets come from environment/secret-management integration; never source-control them.
11. Active user-uploaded content (HTML/SVG/JavaScript) is rejected by the default upload policy.
12. User-controlled CSS/style values are not accepted by framework component APIs.
13. CSP is intentionally not invented by default. A CSP must be certified against NiceGUI's script/WebSocket/static-resource behavior before enabling it.

## Logging & errors

14. Logs use structured fields and correlation IDs.
15. Passwords, tokens, secrets, credentials, authorization headers and cookies are redacted recursively.
16. User-facing errors contain safe messages and error/correlation IDs, not stack traces.
17. Detailed diagnostics are never public by default.

## Reverse proxy & deployment

18. `root_path` is configured centrally and must be certified with HTTP pages, WebSockets, and static assets together.
19. Forwarded headers are trusted only from explicitly configured IPs/networks/literals.
20. Never set `forwarded_allow_ips='*'` in a normal company deployment.
21. NiceGUI stays at one Uvicorn worker per process. Horizontal scaling uses multiple app instances instead.
22. Multiple NiceGUI instances require session affinity/sticky sessions for page/WebSocket continuity.
23. Multiple instances also require shared persistence (Redis or equivalent) when framework/user storage must survive cross-instance routing.
24. Production browser opening, reload mode, autogenerated FastAPI docs, endpoint documentation, and server fingerprint headers are disabled by default.

## Operations

25. `/healthz` is minimal liveness; `/readyz` reports only readiness state.
26. Detailed diagnostics require authentication plus an explicit access policy.
27. Dependency checks are bounded by timeouts and cannot crash the health endpoint.
28. `RuntimeDoctor` findings with error severity are release blockers in the certified environment.
29. `COMPATIBILITY.json` is authoritative for framework/runtime versions and deployment assumptions.
30. Application code must use `RuntimeConfig`; scattered direct environment-variable/runtime configuration is an anti-pattern.

## Current NiceGUI assumptions captured by this milestone

- NiceGUI is pinned to 3.15.0.
- `ui.run` supports `storage_secret`, `session_middleware_kwargs`, and Uvicorn kwargs such as `root_path`.
- NiceGUI currently rejects `workers > 1` for one process.
- Current NiceGUI guidance for multiple instances uses sticky sessions and shared storage such as Redis.
- NiceGUI's security guidance treats the page-created client ID as a session capability; important pages therefore must be authentication-gated before content is emitted.
